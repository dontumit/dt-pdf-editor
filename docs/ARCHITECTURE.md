# สถาปัตยกรรมระบบ

## หลักการออกแบบ

> **Process Locally Whenever Possible, Upload Only When Necessary**

ทุกการตัดสินใจในระบบนี้ย้อนกลับมาที่ประโยคเดียวข้างบน
เพราะผู้ใช้หลักคือหน่วยงานที่ทำงานกับเอกสารสำคัญ — บัตรประชาชน เวชระเบียน เอกสารราชการ
การไม่ส่งไฟล์ขึ้นเซิร์ฟเวอร์ไม่ใช่แค่เรื่องประหยัดทรัพยากร แต่เป็นเรื่องความรับผิดชอบต่อข้อมูลของผู้ใช้

ผลพลอยได้ที่ตามมา
- เซิร์ฟเวอร์รับผู้ใช้พร้อมกันได้มากโดยไม่ต้องขยายเครื่อง เพราะงานหนักอยู่ที่เครื่องผู้ใช้
- ค่าแบนด์วิดท์ต่ำ ไฟล์ 50 MB ไม่ต้องวิ่งขึ้นลง
- เร็วกว่า ไม่ต้องรออัปโหลดและดาวน์โหลด
- ใช้งานออฟไลน์ได้หลังโหลดแอปครั้งแรก

## เส้นแบ่ง: อะไรทำที่ไหน

### ทำบนเบราว์เซอร์ (15 เครื่องมือ)

| งาน | เทคโนโลยี | เหตุผล |
|---|---|---|
| รวม / แยก / จัดหน้า / หมุน / ลบหน้า | pdf-lib ใน Web Worker | เป็นการจัดโครงสร้าง object ของ PDF ไม่ต้องเรนเดอร์ |
| ลายน้ำ / เลขหน้า / ครอบตัด / วางองค์ประกอบ | pdf-lib + fontkit ใน Web Worker | ฝังฟอนต์ไทยได้ครบ ทำงานเร็ว |
| PDF → รูป / ลดขนาด (rasterize) | pdf.js + Canvas | pdf.js มี worker ของตัวเอง การ parse จึงไม่บล็อก UI |
| รูป → PDF / ลดขนาดรูป | Canvas + pdf-lib | ใช้ตัวเข้ารหัสภาพของเบราว์เซอร์โดยตรง |
| สแกนเอกสาร | getUserMedia + Canvas | ดัดมุมด้วย homography ที่เขียนเอง |
| OCR | Tesseract.js (WASM) | เอกสารไม่ออกจากเครื่อง ครั้งแรกโหลดข้อมูลภาษาจาก CDN |

### ทำบนเซิร์ฟเวอร์ (3 เครื่องมือ + 1 ทางเลือก)

| งาน | เครื่องมือ | ทำไมทำบนเบราว์เซอร์ไม่ได้ |
|---|---|---|
| ใส่ / ปลดรหัสผ่าน PDF | `qpdf` | pdf-lib ไม่รองรับการเข้ารหัส PDF |
| PDF → Word | `pdfjs-dist` + `docx` | ต้องประกอบโครงสร้างเอกสารใหม่ ใช้หน่วยความจำสูง |
| OCR ฝั่งเซิร์ฟเวอร์ | `tesseract.js` + `poppler` | สำหรับเครื่องผู้ใช้ที่แรงไม่พอ หรือไฟล์หลายร้อยหน้า |
| บีบอัดคุณภาพสูง | `ghostscript` | คงข้อความไว้ได้ ต่างจากการ rasterize บนเบราว์เซอร์ |

> เครื่องมือฝั่งเซิร์ฟเวอร์เป็น **ทางเลือกทั้งหมด** ระบบตรวจว่ามี binary ตัวไหนติดตั้งอยู่
> แล้วปิดเฉพาะเครื่องมือที่เกี่ยวข้อง พร้อมแสดงสถานะที่หน้า `/status`

## วงจรชีวิตของไฟล์

### เครื่องมือที่ทำงานบนเบราว์เซอร์

```
ผู้ใช้เลือกไฟล์
   → อ่านเป็น ArrayBuffer ในหน่วยความจำของแท็บ
   → ส่งเข้า Web Worker แบบ transfer (ไม่คัดลอก)
   → ประมวลผล
   → ได้ Blob ผลลัพธ์
   → สร้าง Blob URL → ดาวน์โหลด
   → revokeObjectURL() ภายใน 4 วินาที
   → ปิด worker เมื่อออกจากหน้า

ไม่มีไบต์ใดของเอกสารออกจากเครื่องผู้ใช้เลย
เซิร์ฟเวอร์ได้รับเพียง: ชื่อเครื่องมือ จำนวนไฟล์ ขนาดรวม เวลาที่ใช้ และสถานะ
```

### เครื่องมือที่ต้องใช้เซิร์ฟเวอร์

```
อัปโหลด → multer เขียนลง storage/tmp/<sessionId>/
   → ตรวจ magic number (ไม่เชื่อ MIME จากเบราว์เซอร์)
   → ย้ายเข้า storage/jobs/<jobId>/ พร้อมบันทึกลง job_files
   → เข้าคิว (สถานะ WAITING)
   → worker หยิบไปทำ (PROCESSING)
   → ไฟล์ input ถูกลบทันทีที่งานจบ ไม่ว่าสำเร็จหรือล้มเหลว
   → ไฟล์ output อยู่ต่อจนถึง expires_at (ค่าเริ่มต้น 30 นาที)
   → ผู้ใช้ดาวน์โหลด → ระบบเรียก DELETE /api/files/job/:id ให้อัตโนมัติหลัง 12 วินาที
   → cleanup worker กวาดที่เหลือทุก 5 นาที
```

**รหัสผ่านที่ผู้ใช้กรอก** ถูกเก็บใน `Map` ในหน่วยความจำของโปรเซส worker เท่านั้น
ลบทิ้งใน `finally` ของทุกงาน ไม่เคยถูกเขียนลงฐานข้อมูล ไฟล์ หรือ log

## การจัดการหน่วยความจำ

PDF ขนาดใหญ่กินหน่วยความจำมหาศาล ระบบจึงออกแบบไว้หลายชั้น

| กลไก | รายละเอียด |
|---|---|
| Lazy rendering | `IntersectionObserver` เรนเดอร์เฉพาะ thumbnail ที่อยู่ในจอ (`pdf/render.js`) |
| Transferable objects | ส่ง `ArrayBuffer` เข้า worker แบบ transfer ไม่คัดลอก |
| คืน canvas ทันที | ตั้ง `canvas.width = 0` หลังใช้เสร็จ บังคับให้ GC คืนหน่วยความจำ |
| Revoke Blob URL | ทุก URL ถูกติดตามใน `utils/download.js` และถูก revoke ทั้งหมดตอนออกจากหน้า |
| ปิด worker | `releaseWorker()` ถูกเรียกใน cleanup ของทุกหน้าเครื่องมือ |
| ยอมให้ UI หายใจ | `await setTimeout(0)` ทุก 3 หน้าในลูปที่ยาว |
| ข้อความ error เฉพาะทาง | จับ out-of-memory แล้วแนะนำให้ลดจำนวนหน้าหรือใช้เซิร์ฟเวอร์ |

## กลยุทธ์แคช

แยกแคชเป็น 3 ชั้นเพื่อให้ล้างเฉพาะส่วนที่ต้องการได้

| แคช | เนื้อหา | นโยบาย |
|---|---|---|
| `dtpdf-static-<version>` | HTML, CSS, โมดูล JS | stale-while-revalidate |
| `dtpdf-vendor-<version>` | pdf-lib, pdf.js, fontkit, ฟอนต์ | cache-first (ไม่เปลี่ยนภายในเวอร์ชัน) |
| `dtpdf-runtime-<version>` | API สาธารณะ เช่น `/api/status` | network-first |

**ห้ามแคชเด็ดขาด** — จัดการที่ `service-worker.js` ผ่าน `NEVER_CACHE`

```
/api/files/*   /api/jobs/*   /api/history   /api/admin/*
/api/auth/*    /api/heartbeat  /api/visit   /api/vitals   /s/*
```

การเปลี่ยน `CACHE_VERSION` ใน `.env` จะเปลี่ยนชื่อแคชทั้งหมด
service worker ตัวเก่าจะถูกลบใน `activate` และผู้ใช้ได้รับ toast ให้กดอัปเดต

## ระบบนับผู้ใช้ออนไลน์

ไม่ใช้จำนวนแท็บที่เปิดอยู่ เพราะไม่สะท้อนความจริง (แท็บค้างไว้ไม่ได้แปลว่ากำลังใช้งาน)

```
เบราว์เซอร์ ──POST /api/heartbeat──▶ ตาราง presence (session_id, last_seen)
   ทุก HEARTBEAT_INTERVAL วินาที (ค่าเริ่มต้น 25)
   หยุดส่งเมื่อแท็บถูกซ่อน (visibilitychange)

นับออนไลน์ = COUNT(*) WHERE last_seen >= now - ONLINE_TIMEOUT   (ค่าเริ่มต้น 75 วินาที)

cleanup worker ลบแถวที่เก่ากว่า ONLINE_TIMEOUT × 4 ทุก 5 นาที
```

ตัวเลขบนหน้าเว็บทั้งหมดมาจากตารางนี้และตาราง `daily_stats` โดยตรง
**ไม่มีตัวเลขจำลองหรือค่าสุ่มอยู่ในระบบเลย** — ถ้าไม่มีผู้ใช้ ตัวเลขจะเป็น 0

## คิวงานฝั่งเซิร์ฟเวอร์

ใช้ SQLite เป็นคิว เพื่อให้ติดตั้งได้โดยไม่ต้องมี Redis

```sql
-- หยิบงานถัดไปแบบ atomic ป้องกัน worker หลายตัวหยิบงานเดียวกัน
BEGIN;
  SELECT COUNT(*) FROM jobs WHERE status='PROCESSING' AND mode='server';  -- เทียบกับ MAX_CONCURRENT_JOBS
  SELECT * FROM jobs WHERE status='WAITING' AND mode='server' ORDER BY created_at LIMIT 1;
  UPDATE jobs SET status='PROCESSING', started_at=?, attempts=attempts+1 WHERE id=?;
COMMIT;
```

- ทุกงานมี `PROCESSING_TIMEOUT_SECONDS` ถ้าเกินจะถูกยกเลิกและลบไฟล์
- งานที่ค้างสถานะ `PROCESSING` ตอนเซิร์ฟเวอร์รีสตาร์ท จะถูกส่งกลับเข้าคิว
  หรือทำเครื่องหมายล้มเหลวถ้าลองมาแล้ว 2 ครั้ง (`recoverStuckJobs()`)
- แยกเป็น container ต่างหากได้ด้วย `RUN_INLINE_WORKER=false` + `workers/standalone.js`

**การย้ายไป Redis/BullMQ ในอนาคต** แก้เฉพาะ `workers/queue.js`
ตัว processor ทุกตัวรับ context เหมือนเดิม (`{ inputs, outDir, params, secrets, onProgress }`) จึงไม่ต้องแก้

## ความปลอดภัย

| ชั้น | การป้องกัน |
|---|---|
| Transport | HSTS, redirect เป็น HTTPS ที่ nginx |
| Headers | CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors` |
| CSRF | double-submit cookie ทุก request ที่เปลี่ยนสถานะ (ยกเว้น LINE callback) |
| Session | JWT ใน cookie `HttpOnly` + `SameSite=Lax` + `Secure` |
| ไฟล์ | ตรวจ magic number, จำกัดขนาด, จำกัดจำนวน, ทำชื่อไฟล์ให้ปลอดภัย |
| อัตราคำขอ | rate limit รายชั่วโมงในแอป + burst limit รายเส้นทาง + `limit_req` ที่ nginx |
| การประมวลผล | timeout ต่องาน, จำกัดงานพร้อมกัน, ยกเลิกได้เสมอ |
| ความลับ | ทั้งหมดอยู่ใน environment, logger ปิดบังคีย์อ่อนไหวอัตโนมัติ |
| PDPA | ไม่เก็บ IP, hash LINE userId, ลบข้อมูลดิบตามระยะเก็บรักษา, ผู้ใช้ลบประวัติเองได้ |

## การขยายระบบ

ระบบออกแบบให้รองรับผู้ใช้เพิ่มขึ้นโดยไม่ต้องเขียน frontend ใหม่

| จำนวนผู้ใช้ | สิ่งที่ต้องทำ |
|---|---|
| ~100 | เครื่องเดียว SQLite, `RUN_INLINE_WORKER=true` — ค่าเริ่มต้นใช้ได้เลย |
| ~1,000 | แยก worker เป็น container ต่างหาก, ตั้ง nginx ทำ TLS และแคช static |
| ~10,000 | ย้าย DB เป็น PostgreSQL (แก้เฉพาะ `db/index.js`), ใช้ Redis เก็บ presence + queue, ขยาย app แนวราบหลาย instance หลัง load balancer, ย้าย static ไป CDN |

จุดสำคัญคือ **API เป็น stateless** — สถานะทั้งหมดอยู่ในฐานข้อมูลและ cookie
การเพิ่ม instance จึงทำได้ทันทีโดยไม่ต้องทำ sticky session
